# Security Analysis — MultiSigTimelockWallet

## 1. Hostile Security Audit Summary

We reviewed `contracts/MultiSigTimelockWallet.sol` against 11 threat vectors common to multi-signature wallets and time-lock controllers. Note on static analysis tooling: `slither-analyzer` is not installed in the offline build environment (`pip install slither-analyzer` requires internet access), so we performed a manual line-by-line audit combined with automated adversarial testing (`T1`–`T23`, including `ReentrancyAttacker.sol`).

| # | Issue / Threat Vector | Severity | Where in Code | Status | Plain-Words Explanation |
| :- | :--- | :--- | :--- | :--- | :--- |
| 1 | **Reentrancy on external ETH transfer** | Critical | `execute()` (`nonReentrant` modifier + `txn.status = Status.Executed` before `.call`) | **Fixed / Protected** | A malicious recipient contract might call `execute()` again inside its `receive()` fallback to drain the wallet. We stop this in two ways: we mark `status = Executed` before sending ETH (Checks-Effects-Interactions) and we lock `execute()` with a `nonReentrant` boolean guard (`_locked`). Verified by test `T20`. |
| 2 | **Double execution of a proposal** | High | `execute()` (`if (txn.status != Status.Queued) revert NotQueued();`) | **Fixed / Protected** | Once a transaction runs, its status changes from `Queued` to `Executed`. Any second attempt to run it immediately reverts with `NotQueued`. Verified by test `T11`. |
| 3 | **Double approval or double cancel-vote by one owner** | High | `approve()` (`approved[id][msg.sender]`) and `voteCancel()` (`cancelVoted[id][msg.sender]`) | **Fixed / Protected** | Each owner's vote is stored in a `mapping(uint256 => mapping(address => bool))`. If the same owner tries to approve or cancel-vote twice on the same transaction, the contract reverts with `AlreadyApproved`. Verified by `T8` and `T16b`. |
| 4 | **Timer left running after revocation ("Approve-then-Revoke" trick)** | High | `revoke()` and `sync()` (`if (txn.status == Status.Queued && _approvalCount(id) < threshold)`) | **Fixed / Protected** | If an owner revokes their approval while a transaction is `Queued` and active approvals fall below `threshold`, the contract immediately resets `status = Status.Pending` and `unlockTime = 0`. Re-approving later starts a brand-new countdown from the new approval timestamp. Verified by `T13` and `T14`. |
| 5 | **Stale queued transactions executed months later** | Medium | `execute()` and `isExpired()` (`block.timestamp > txn.unlockTime + GRACE_PERIOD`) | **Fixed / Protected** | A queued transaction that is not executed within `GRACE_PERIOD` (7 days) after `unlockTime` becomes expired. Calling `execute()` after the grace window reverts with `Expired`, and `getStatus(id)` returns `5`. Verified by `T12`. |
| 6 | **Approvals from removed owners counting toward execution** | High | `_approvalCount()` and `_cancelCount()` + `execute()` + `sync()` | **Fixed / Protected** | Instead of storing a static counter, `_approvalCount(id)` loops over the current `owners` array and counts only active owners. When an owner is removed via `removeOwner()`, their past approval is immediately ignored, `execute()` re-checks `_approvalCount(id) >= threshold`, and `sync(id)` demotes the transaction back to `Pending`. Verified by `T22`. |
| 7 | **Invalid threshold or owner list locking the wallet** | High | `constructor`, `addOwner`, `removeOwner`, `changeThreshold` | **Fixed / Protected** | Every owner or threshold change enforces `3 <= owners.length <= 10` and `2 <= threshold <= owners.length`. This prevents a 1-of-N wallet (which would bypass multi-sig) and prevents setting `threshold` higher than the number of owners (which would lock funds forever). Verified by `T2`, `T3`, `T3b`, `T18c`, and `T19`. |
| 8 | **Outsiders or single owners calling governance functions** | Critical | `addOwner`, `removeOwner`, `changeThreshold`, `changeDelay` (`onlySelf` modifier) | **Fixed / Protected** | All four governance functions have the `onlySelf` modifier (`msg.sender == address(this)`). No external user or single owner can call them directly; they can only run as the payload of a time-locked proposal targeting the wallet itself. Crucially, governance functions do **not** have `nonReentrant` because they run inside `execute()`, which already holds the lock. Verified by `T17` and `T18`. |
| 9 | **Failed external calls marking transaction Executed and trapping ETH** | High | `execute()` (`if (!ok) revert ExecutionFailed();`) | **Fixed / Protected** | If the target contract reverts or runs out of gas during `to.call{value: value}(data)`, `execute()` reverts with `ExecutionFailed()`. Because EVM reverts are atomic, the `status = Status.Executed` change is rolled back and the transaction remains `Queued` so it can be retried before expiry. Verified by `T19`. |
| 10 | **Unbounded loops exhausting block gas limit** | Medium | `MAX_OWNERS = 10` enforced in `constructor` and `addOwner` | **Fixed / Protected** | Looping over `owners` in `_approvalCount`, `_cancelCount`, and `removeOwner` is strictly bounded to at most 10 iterations, costing negligible gas and preventing Denial-of-Service (DoS) via gas exhaustion. Verified by `T3b`. |
| 11 | **Miner / Validator timestamp manipulation** | Low | `approve()`, `execute()`, `MIN_DELAY = 10 seconds` | **Accepted (Inherent to EVM)** | Block proposers can shift `block.timestamp` by roughly 15 seconds. For a 60-second demo delay or a real-world multi-hour/multi-day delay and a 7-day grace period, a few seconds of drift does not weaken the security guarantee. |

## 2. Known Limitations (Honest Disclosure for Viva & Report)

1. **Re-added Owner Old Flags**: Because `approved[id][owner]` and `cancelVoted[id][owner]` are stored in nested mappings keyed by address, if an owner is removed via `removeOwner` and that **same address** is later added back via `addOwner` while an old transaction `id` is still active, their previous `true` flag on that old transaction `id` will count again. Clearing all historical transaction mappings on owner removal would require an unbounded loop over `txCount`, so this trade-off is intentionally accepted and documented.
2. **Lost Private Keys**: If more than `N - M` owners permanently lose their MetaMask private keys, the remaining owners cannot reach `threshold` (`M`), and funds in the wallet will be permanently locked. Users should choose a balanced threshold (such as 2-of-3 or 3-of-5).
3. **On-Chain Gas Cost per Approval**: Every approval and cancellation vote is an on-chain transaction that costs gas. Production wallets like Safe (formerly Gnosis Safe) support off-chain EIP-712 signature aggregation to save gas.
4. **No Built-In Upgradeability**: The contract is deployed as a standalone immutable contract without a proxy pattern so the codebase remains simple, transparent, and easy to verify in Remix.
